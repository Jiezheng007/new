# 体系结构测试计划 (Test Plan)

本文档明确了针对“可用性”、“可修改性”和“性能”三大质量属性的测试场景及验证标准。

## 1. 性能测试 (Performance Testing)

*   **测试目的**：验证系统在并发环境下的吞吐量、响应时间，以及异步任务是否有效避免了接口阻塞。
*   **测试场景**：
    *   **场景 1：核心页面高并发访问**。模拟多用户并发拉取工作台数据 (`/api/dashboard`)。
    *   **场景 2：耗时任务不阻塞验证**。模拟用户发起“生成报告”请求 (`/api/reports`)。
*   **测试工具**：`Locust` (在 `scripts/locustfile.py` 中定义)
*   **期望结果**：
    *   在设定的并发数（如 50-100 用户）下，核心读取接口的 P95 响应时间保持在可接受范围（如 < 500ms）。
    *   生成报告接口能迅速返回任务创建成功的状态（如 < 200ms），证明采用了异步处理，不阻塞系统。

## 2. 可用性测试 (Availability Testing)

*   **测试目的**：验证系统在面临局部故障时的容错能力和稳定性。
*   **测试场景**：
    *   **场景 1：外部依赖/处理组件宕机**。假设 NLP 情感分析服务出现超时异常，验证系统整体是否存活。
*   **测试工具**：`Pytest` + `unittest.mock` (在 `scripts/test_availability.py` 中定义)
*   **期望结果**：
    *   当强制注入异常时，舆情接入流程不会导致整个后台进程崩溃（Crash）。
    *   系统能合理捕获异常，将相关任务标记为失败待重试，并继续处理后续请求。

## 3. 可修改性测试 (Modifiability Testing)

*   **测试目的**：通过代码维度的客观数据，证明系统的模块化设计使得代码易于理解和变更。
*   **测试场景**：
    *   **场景 1：代码圈复杂度与维护性指数扫描**。通过静态分析验证单个函数的逻辑复杂度，以及整体模块的维护难易度。
*   **测试工具**：`Radon` (在 `scripts/run_modifiability_test.bat` 中定义)
*   **期望结果**：
    *   核心业务逻辑目录的平均圈复杂度为 A 级（复杂度低，极易修改）。
    *   维护性指数（Maintainability Index）分数处于良好区间（> 80分）。
